TPT App Media QC

1. Product Definition

Product name: TPT Media QC
Repository: tpt-app-media-qc
Product family: TPT Apps
Category: Professional media quality-control and validation
Primary distribution: Offline desktop application
Secondary interfaces: CLI and local watch-folder/automation interface
Target platforms: Windows first; Linux second; macOS only when the underlying TPT media stack is sufficiently mature

1.1 Executive summary

TPT Media QC is a native, offline-first professional application for automated quality control of audio-visual media assets.

The application ingests media files, executes deterministic technical and perceptual checks, presents failures at exact time/frame locations, and produces auditable reports suitable for post-production, broadcast, OTT delivery, archival, advertising, and professional media workflows.

The application is not intended to be another media player or video editor. Its core value proposition is:

Find technical and quality defects before the customer, broadcaster, archive, platform, or audience does.

The application should be substantially more capable than a simple metadata checker while remaining easier to deploy than enterprise media-QC platforms.

The product should process media entirely on the user's machine by default. No upload to TPT infrastructure is required.

2.2 Competitive positioning

Existing products such as Telestream Vidchecker, Interra BATON, Venera Pulsar, QScan and newer desktop QC tools demonstrate that automated media QC is an established professional category. Existing systems cover technical compliance, audio/video analysis, reporting, watch folders and broadcast standards. citeturn0search2turn0search6turn0search12

TPT should therefore not attempt to win merely by implementing another list of media checks.

The differentiators should be:

Native Rust implementation.

Offline-first operation.

No mandatory cloud upload.

Excellent performance on commodity hardware.

Extremely clear operator workflow.

Exact frame/timecode navigation from every finding.

Unified video, audio, voice and media analysis.

Highly configurable QC profiles.

Reproducible deterministic reports.

Strong developer/CLI automation.

Open-source TPT media foundations underneath a commercial application.

Simple licensing compared with enterprise media platforms.

A current desktop competitor already markets local processing, native Windows/macOS support, 8K, HDR, multiple containers/codecs and PDF/Excel reporting, so those capabilities alone must not be treated as the product's moat. citeturn0search1

3. Product Principles

3.1 Offline first

All core analysis must work without internet access.

The application must not require:

cloud media storage

remote rendering

remote AI APIs

account creation

telemetry

cloud licensing checks

Internet connectivity may optionally be used for:

software updates

licence activation

downloading standards profiles

optional model updates

The user must be able to disable these features.

3.2 Deterministic technical analysis

Technical checks should produce the same result for the same:

input bytes

application version

QC profile

analysis configuration

Results must include enough provenance to reproduce the decision.

3.3 Explain every failure

A result must never simply say:

FAILED

It must explain:

what failed

why it failed

threshold/configuration

measured value

expected value

timecode/frame

affected stream/channel

severity

confidence where applicable

3.4 Do not hide uncertainty

Perceptual/heuristic checks must distinguish:

PASS

WARN

FAIL

INCONCLUSIVE

Do not convert uncertain computer-vision/audio analysis into a false binary result.

3.5 Analysis and presentation are separate

The QC engine must be usable without the desktop GUI.

7. QC Rule Architecture

Rules must be plugins/components in the application architecture.

trait QcRule {
    fn id(&self) -> RuleId;
    fn description(&self) -> RuleDescription;
    fn required_capabilities(&self) -> Capabilities;
    fn execute(&self, context: &QcContext) -> RuleResult;
}

Rules should declare:

required streams

required decode capabilities

whether they need full-frame access

whether they can operate on metadata only

whether they can operate incrementally

GPU requirements

expected computational cost

This allows the scheduler to optimise execution.

16. Automation Interface

The CLI should be first-class, not an afterthought.

Example:

tpt-media-qc check \
  --profile client-a.yaml \
  --input episode-01.mov \
  --report episode-01.json

Batch:

tpt-media-qc batch \
  --profile client-a.yaml \
  --input ./incoming \
  --output ./reports

Machine-readable result:

{
  "status": "fail",
  "asset": "episode-01.mov",
  "profile": "client-a",
  "findings": 3
}

Exit codes:

0 = PASS
1 = WARN
2 = FAIL
3 = INCONCLUSIVE
4 = CONFIGURATION_ERROR
5 = INPUT_ERROR
6 = INTERNAL_ERROR

The exit-code contract must remain stable.

19. Caching

Caching is important for expensive analysis.

Cache keys should include:

asset fingerprint
application version
ruleset version
profile hash
analysis configuration hash

If any component changes, invalidate only affected results.

Example:

same asset
same profile
same rules
        |
        +--> reuse existing QC result

But changing:

black-frame threshold

should invalidate only the affected rule, not necessarily the entire analysis.

20. Performance Targets

Initial targets should be treated as engineering goals rather than guarantees.

Metadata scan

Begin displaying results within 1 second for ordinary files.

Process large batches concurrently.

Full QC

Aim for faster-than-real-time processing for common technical checks on commodity modern hardware.

Expensive perceptual checks may legitimately be slower.

Memory

Do not scale memory linearly with media duration.

A 2-hour video should not require 2 hours of decoded frames in RAM.

Concurrency

Use all useful CPU cores while respecting user-configurable limits.

Avoid starving the desktop UI.

GPU

GPU acceleration should be optional.

CPU execution must remain correct.

21. Failure Handling

A single corrupt asset must not terminate a batch.

Each job must have an isolated failure state.

Example:

Batch
 ├── file01 PASS
 ├── file02 PASS
 ├── file03 FAIL
 ├── file04 INPUT_ERROR
 └── file05 PASS

The batch itself completes.

Internal panics should be treated as application defects and captured through crash reporting only if the user explicitly enables it.

30. Definition of Done

The first release is ready for paid users when:

A user can install the application without development tooling.

A user can drag a media file into the application.

The application can inspect all supported streams.

A QC profile can be selected or created.

A complete QC job can run offline.

Multiple files can be processed concurrently.

A failure identifies an exact time/frame when applicable.

Findings include measured and expected values where applicable.

The user can navigate directly from a finding to evidence.

Reports can be exported to PDF and JSON.

The CLI can run the same QC engine as the GUI.

Watch-folder processing works.

A corrupt media file cannot crash the entire batch.

Golden-media tests cover every production rule.

Fuzz testing covers parsers and media-boundary code.

Results are reproducible from asset fingerprint + profile + application/ruleset version.

No internet connection is required for core operation.

A clean-machine installation has been tested.

Performance has been benchmarked against representative HD/UHD files.

32. Strategic Constraint

Do not attempt to match every feature of Vidchecker/BATON/Pulsar on version 1.

Those products have years of standards coverage and enterprise integrations. Current competitors demonstrate that broad broadcast compliance, HDR, IMF, DPP/AS-11 and advanced audio/video testing are already expected in the high end of this category. citeturn0search2turn0search6turn0search12

TPT's first advantage should instead be:

A modern, extremely fast, offline, developer-friendly QC engine with a dramatically better operator experience.

Then use the open TPT media foundation to expand coverage rapidly.

The commercial application should be the place where these foundations become a coherent professional product.
